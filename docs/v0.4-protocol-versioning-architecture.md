# v0.4 — protocolversionering & historische reproduceerbaarheid

## Doel

v0.4 maakt controleprotocollen historisch reproduceerbaar.

Een Check moet exact kunnen reconstrueren welke versie van een Protocol en welke controlepunten op het moment van uitvoering golden.

**Kernregel:** een ProtocolVersion wordt immutable zodra ze door een Check gebruikt is. Een inhoudelijke wijziging krijgt altijd een nieuwe ProtocolVersion.

## Kernmodel

**Project → Task → Source → SourceVersion → Check → ProtocolVersion → ProtocolItem → CheckResult → Review**

### Protocol

Een Protocol is het logische, herbruikbare controleconcept.

Velden:
- `id`
- `name`
- `description`
- `active`
- `createdAt`
- `updatedAt`

### ProtocolVersion

Een concrete historische versie.

Velden:
- `id`
- `protocolId`
- `version`
- `description`
- `status`
- `createdAt`

Statussen:
- `draft`
- `active`
- `retired`

Een gebruikte versie kan niet terug naar `draft`.

### ProtocolItem

Een ProtocolItem behoort tot exact één ProtocolVersion.

Velden:
- `id`
- `protocolVersionId`
- `order`
- `title`
- `description`
- `required`
- `createdAt`

Items van een gebruikte versie zijn immutable.

## Check

Een Check verwijst naar één specifieke ProtocolVersion via `protocolVersionId`.

De bestaande `protocolVersion`-snapshot blijft voorlopig behouden voor backward compatibility en historische metadata.

Een Check maakt CheckResults aan voor de ProtocolItems van die specifieke versie.

## Versieregels

1. Een bestaande ProtocolVersion wordt niet inhoudelijk overschreven.
2. Nieuwe inhoud betekent een nieuwe versie.
3. Zodra een versie door een Check gebruikt is, kunnen inhoud en items niet meer gewijzigd of verwijderd worden.
4. Een nieuwe versie kan de items van een bestaande versie kopiëren, met nieuwe IDs.
5. Nieuwe versies mogen geen oude CheckResults of Reviews wijzigen.
6. Een retired versie blijft leesbaar.

## Migratie v0.3 → v0.4

Bestaande data moet behouden blijven.

De migratie:
1. behoudt alle bestaande Protocols;
2. maakt voor elk bestaand Protocol een ProtocolVersion op basis van de huidige `protocol.version`;
3. koppelt bestaande ProtocolItems aan die versie;
4. voegt `protocolVersionId` toe aan bestaande Checks;
5. behoudt de bestaande `protocolVersion`-waarde;
6. verwijdert geen Checks, CheckResults of Reviews.

De migratie moet idempotent zijn: herhaald laden mag geen dubbele versies of koppelingen veroorzaken.

## Interface

Een Protocol wordt weergegeven als verzameling versies.

Voorbeeld:

**Wiskundige correctheid**
- v1.0 — retired
- v1.1 — active
- v2.0 — draft

Een nieuwe versie kan worden gemaakt door een bestaande versie te kopiëren.

Bij het starten van een Check wordt een concrete ProtocolVersion geselecteerd.

## Functionele eisen

### Protocolbeheer
- Protocols kunnen zonder versie bestaan.
- Versienummers zijn uniek binnen een Protocol.
- Een nieuwe versie kan worden toegevoegd of gekopieerd.

### ProtocolItems
- Items behoren aan één versie.
- Items hebben een stabiele volgorde.
- Draft-items zijn wijzigbaar zolang de versie ongebruikt is.
- Gebruikte items zijn immutable.

### Checks
- Elke Check gebruikt exact één ProtocolVersion.
- CheckResults horen bij items van die versie.
- Oude Checks blijven intact wanneer nieuwe versies ontstaan.

### Historische integriteit
- Geen wijziging van oude CheckResults door nieuwe protocolversies.
- Geen wijziging van oude Reviews.
- Gebruikte versies kunnen niet verwijderd worden.

## Besluit

v0.4 legt de versioneringsfundering voor een reproduceerbaar kwaliteitsplatform.

Inhoud wordt nooit achteraf herschreven. Elke inhoudelijke wijziging krijgt een nieuwe versie, terwijl bestaande Checks, CheckResults en Reviews naar hun historische versie blijven verwijzen.

Verdere automatisering wordt pas gebouwd nadat deze fundering stabiel is.
