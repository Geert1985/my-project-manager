# v0.2 — bron- en controlearchitectuur

## Doel

v0.2 voegt geen complexe interface toe voordat het onderliggende datamodel vastligt.

De applicatie moet projecten kunnen beheren waarvan onderdelen gebaseerd zijn op documenten, bronnen en controleprotocollen. Een controle moet reproduceerbaar zijn: we moeten later kunnen zien **wat** gecontroleerd werd, **tegen welke bronversie**, **met welk protocol**, **wanneer** en **met welk resultaat**.

## Kernmodel

De relatie wordt:

**Project → Task → Source → SourceVersion → Check → Review**

Een Task blijft het centrale werkobject. Sources en Checks zijn ondersteunende objecten die aan een task kunnen worden gekoppeld.

### 1. Project

Een project groepeert alle werkzaamheden.

Velden:
- `id`
- `name`
- `description`
- `category`
- `status`
- `priority`
- `createdAt`
- `updatedAt`

### 2. Task

De bestaande task-engine blijft behouden.

Velden:
- `id`
- `projectId`
- `parentId`
- `name`
- `description`
- `status`
- `priority`
- `completionMode`
- `createdAt`
- `completedAt`

Een Task kan optioneel bronnen en controles hebben.

### 3. Source

Een Source beschrijft een bron als logisch object.

Voorbeelden:
- een cursusbestand
- een boek
- een wetenschappelijk artikel
- officiële documentatie
- een GitHub-bestand
- een website

Velden:
- `id`
- `projectId`
- `taskId` — optioneel
- `type`
- `title`
- `author`
- `publisher`
- `url`
- `description`
- `createdAt`
- `updatedAt`

Belangrijk: Source is **niet** hetzelfde als een concrete versie van een bestand.

### 4. SourceVersion

Een SourceVersion legt een specifieke toestand van een Source vast.

Velden:
- `id`
- `sourceId`
- `version`
- `label`
- `contentHash` — optioneel
- `fileName` — optioneel
- `filePath` — optioneel
- `url` — optioneel
- `createdAt`
- `notes`

Voorbeeld:

Source:
> Fase 6 — cursus

Versies:
- v1.0 — eerste versie
- v1.1 — correcties
- v1.2 — uitbreiding
- v1.3 — gecontroleerde versie

Een controle verwijst altijd naar een **SourceVersion**, niet alleen naar Source.

### 5. Protocol

Een Protocol definieert hoe iets gecontroleerd moet worden.

Voorbeelden:
- Wiskundige correctheid
- Volledigheid
- Didactische kwaliteit
- Diepgang
- Consistentie
- JavaScript-implementatie

Velden:
- `id`
- `name`
- `description`
- `version`
- `active`
- `createdAt`
- `updatedAt`

Een protocol is dus een herbruikbare controledefinitie.

### 6. ProtocolItem

Een Protocol bevat meerdere concrete controlepunten.

Velden:
- `id`
- `protocolId`
- `order`
- `title`
- `description`
- `required`

Voorbeeld protocol **Wiskundige correctheid**:

1. Definities zijn correct.
2. Notatie is consistent.
3. Beweringen zijn correct.
4. Formules zijn correct.
5. Voorbeelden zijn correct.
6. Berekeningen bevatten geen fouten.
7. Er ontbreken geen noodzakelijke voorwaarden.

### 7. Check

Een Check is een concrete uitvoering van een Protocol op een specifieke SourceVersion.

Velden:
- `id`
- `taskId`
- `sourceVersionId`
- `protocolId`
- `protocolVersion` — vastgelegde protocolversie op het moment van de controle
- `status`
- `startedAt`
- `completedAt`
- `summary`

Statussen:
- `not_started`
- `in_progress`
- `passed`
- `failed`
- `blocked`

Een Check is dus geen protocol. Het is een **uitgevoerde controle**.

### 8. CheckResult

Elke ProtocolItem krijgt tijdens een Check een resultaat.

Velden:
- `id`
- `checkId`
- `protocolItemId`
- `status`
- `comment`
- `evidence`
- `createdAt`
- `updatedAt`

Statussen:
- `not_checked`
- `pass`
- `fail`
- `not_applicable`

Hierdoor kan één controle gedeeltelijk goed en gedeeltelijk fout zijn.

### 9. Review

Een Review is de formele beoordeling van een Check.

Velden:
- `id`
- `checkId`
- `status`
- `reviewer`
- `comment`
- `createdAt`

Statussen:
- `pending`
- `approved`
- `rejected`

Een Review is bewust gescheiden van een Check. Een controle kan technisch uitgevoerd zijn terwijl de eindbeoordeling nog moet gebeuren.

Reviewregels:
- Alleen een afgeronde Check (passed of failed) kan gereviewd worden.
- Een passed Check kan worden goedgekeurd of afgewezen.
- Een failed Check kan niet worden goedgekeurd; er moet een nieuwe bronversie en nieuwe Check komen.
- Een review met status approved of rejected is immutable.
- De Check bewaart de protocolversie waarmee de controle gestart werd.

## Voorbeeld: From Zero 2 Infinity

Een vereenvoudigd voorbeeld:

Project:
> From Zero 2 Infinity

Task:
> Fase 6 — Differentiaalrekening

Subtask:
> Milestone 6.4 — Afgeleiden

Source:
> Milestone 6.4 cursus

SourceVersion:
> v1.3

Check:
> Wiskundige correctheid v2

ProtocolItems:
- Definities correct → pass
- Formules correct → pass
- Voorbeelden correct → fail
- Notatie consistent → pass

Check:
> failed

Review:
> rejected

Commentaar:
> Voorbeeld 3 bevat een fout in de afgeleide van de samengestelde functie.

Na correctie:

SourceVersion:
> v1.4

Nieuwe Check:
> Wiskundige correctheid v2

Resultaat:
> passed

Dit maakt de geschiedenis reproduceerbaar.

## Belangrijke ontwerpregels

### Regel 1 — Versies mogen nooit overschreven worden

Een nieuwe inhoudelijke versie krijgt een nieuwe SourceVersion.

### Regel 2 — Checks zijn immutable historiek

Een afgeronde Check wordt niet achteraf aangepast om de geschiedenis te veranderen. Een nieuwe controle wordt uitgevoerd op een nieuwe versie.

### Regel 3 — Protocolversies zijn belangrijk

Wanneer een protocol verandert, moet een oude controle blijven verwijzen naar de protocolversie waarmee ze uitgevoerd werd.

Daarom moet uiteindelijk ook ProtocolVersion als afzonderlijk object worden overwogen.

### Regel 4 — Task blijft onafhankelijk

Een Task bestaat ook zonder Source of Check.

Dit houdt de algemene projectmanager bruikbaar voor gewone projecten.

### Regel 5 — Geen FZ2I-specifieke code

De checklist-app mag niet afhankelijk worden van termen als `fase`, `milestone` of `wiskundige correctheid`.

Die worden als data ingevoerd.

## Waarom deze volgorde

De applicatie wordt uiteindelijk gebruikt voor tientallen domeinen, honderden milestones en mogelijk duizenden controlepunten.

Daarom moet de **datalaag eerst correct zijn**. De interface kan daarna bovenop dit model worden gebouwd zonder dat we de fundering opnieuw moeten ontwerpen.

## Besluit

v0.2 wordt geen grote UI-update.

Het wordt eerst een **data- en controlelaag** waarmee My Projects kan evolueren van een eenvoudige checklist naar een reproduceerbaar kwaliteits- en reviewplatform.
